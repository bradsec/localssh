# iPhone Safari text editing on the live terminal

Researching: iPhone Safari terminal text interaction to answer Apple’s gestures, WebKit’s behavior, four architectures, and the smallest viable change; for the mobile copy/paste decision; out of scope: implementation and non-iOS platforms.

Source retrieval date: **2026-11-02** throughout. “Keyboard shown” means the on-screen keyboard is visible and the xterm helper textarea has focus. “Keyboard hidden” means it is dismissed; focus must be checked separately. The iPhone observations below came from the project brief, not from a device available to this research. Status applies to each finding, not to a proposed design. Confidence grades assess the conclusion, separately from source reliability.

## Answers

### Q1. Apple’s documented interaction, **HIGH** for editable text; **MED** for non-editable text

- **F1 FACT.** For text in an editable field, Apple’s iOS 26 guide says double-tap selects a word, triple-tap selects a paragraph, and double-tap-and-hold then dragging the grab points selects a block. Tapping selected text exposes editing options, including Copy. The guide also says tap places the insertion point; touch-and-hold magnifies and moves it [S1, S2]. Apple’s iOS 17 selection UI description includes the caret, highlight, handles, and loupe [S3]. This describes Apple’s app/UI model, not a guarantee for every web element or every intermediate iOS version.
- **F2 FACT.** Apple’s HIG says the iOS edit menu can appear when people touch-and-hold **or** double-tap to select content, and encourages selection and copying of non-editable text [S4]. `UITextInteraction` explicitly has distinct editable and non-editable modes; `UITextView`/`UITextField` provide built-in selection and edit-menu interaction [S3, S5, S6]. The HIG does not promise that double-tap selects a word in *all* non-editable web text [S4, S8].
- **F3 FACT.** Paste is an action at an insertion point or empty selection in an editable responder, conditional on available pasteboard content [S4, S6, S7]. Apple’s iPhone guide says tap where the text should go, then tap Paste; the Pages guide gives a concrete two-step example: first reveal an insertion point, tap it again, then Paste [S2, S7]. Therefore “one tap at the same location shows Paste” is **not** a universal rule for an unfocused field. It is plausible for an already focused field with a caret, with a further tap or touch-and-hold sometimes needed. Apple does not document one invariant tap count for Safari textareas across iOS 17-26 [S1, S2, S7].
- **F4 FACT.** A read-only `UITextView` can still be selectable, and UIKit separates selection interaction from editability [S5, S8]. Paste belongs to an editable target, not to static terminal output [S6, S7].

### Q2. WebKit mapping and suppressors, **MED**

- **F5 FACT.** A 2018 WebKit change explicitly disabled its double-tap text-selection gesture in **non-editable web content**, while adding tests for double-tap selection and dragging in editable content [S9, S10]. A 2019 change lets a tap on an existing non-editable selection toggle the Copy callout instead of clearing the selection [S11]. WebKit still has separate native text selection and zoom/double-click gesture paths in current `WKContentViewInteraction.mm` [S12]. **PROBABLE:** treating double-tap on a plain DOM output layer as guaranteed word selection on current Safari is unsound. The old change does not prove that every iOS 17-26 build behaves identically; a physical iPhone must settle this.
- **F6 FACT.** WebKit suppresses iOS native selection handles, highlight, callout, and selection gestures for near-transparent *focused editable* roots. Its 2018 change defines the opacity test using a threshold near 0.01, including ancestor opacity [S13]. A later change suppresses the assistant for tiny editable roots, with a 1×1 px test [S14]. A further change covers fully clipped editable controls [S15]. These are documented mechanisms, not proof that `color: transparent` by itself suppresses the callout. The cited changeset does not establish a general “under 4 px area” rule, so that number is **SUSPECTED** until confirmed against current source or a targeted test [S14].
- **F7 FACT.** `user-select: none` prevents ordinary text selection; `-webkit-touch-callout: none` requests suppression of the long-hold callout; `pointer-events: none` prevents a layer from being the hit target [S16, S25]. The callout property’s documented example is a link menu, so it does not prove suppression of every editing menu. Pointer cancellation can stop compatibility mouse events, and the project’s phone log says `preventDefault()` on `pointerdown` stopped native long-press selection [S16, S17, S19]. `touch-action: none` disables browser pan/zoom defaults, but its effect on a particular text-selection gesture is not settled by that property alone [S17]. For this project, parent `.terminal-host` and descendant overrides must be tested together on Safari [S19].
- **F8 PROBABLE.** WebKit’s selection assistant follows the active editable context and its selection geometry [S3, S12-S15]. The reported iPhone sequence, DOM selection on the output layer with no visible handles/Copy until the xterm textarea’s keyboard was dismissed, is consistent with competing editable focus [S19]. The log does **not** prove a universal WebKit prohibition on selecting non-editable text while another editable is focused. Blurring after selection cleared the range in this device test; using blur as a Copy-menu fix is therefore contradicted by the project evidence [S19].
- **F9 FACT.** The terminal creates xterm with `screenReaderMode: true`, uses the DOM renderer by default, mirrors visible row nodes into `.terminal-touch-text`, freezes the mirror during a selection, and stretches xterm’s helper textarea over the prompt row [S18, S19]. The host uses `touch-action: none` and disables selection/callout; the layer and field override selection/callout, while `.terminal-touch-text` makes text transparent [S19]. A capture-phase `paste` listener sends clipboard data once through `term.paste` to preserve bracketed paste [S19].
- **F10 PROBABLE.** The first-login rectangle is related to the newly opaque helper textarea, but its exact painted part is **SUSPECTED**. Local xterm CSS already sets padding/border/margin to zero, `resize: none`, `overflow: hidden`, and `z-index: -5`; local CSS changes opacity to 1 and width to 100%, leaving possible native focus/appearance painting or an IME/composition view [S19, S20]. Inspect a screenshot plus computed `outline`, `appearance`, `background`, dimensions, and focus state on the device before attributing it to a focus ring or autofill. Transparent text and background do not guarantee the entire native control is invisible [S20].
- **F11 FACT.** WebKit documents `navigator.clipboard` as unavailable to ordinary `http://` pages because the asynchronous Clipboard API needs a secure context [S21]. A user-invoked native Paste event on an editable target can supply `clipboardData`, which the existing handler uses [S19, S22].

### Q3. Architecture options, **MED** for constraints; **LOW** for untested gesture outcomes

Each cell reports the proposed behavior for **double-tap select; handles; Copy; tap-for-Paste**, in that order. “Expected” is an inference, not a passed iPhone test. “Unproven” means the user requirement remains open. A native Copy menu requires an actual selectable text range; Paste requires an editable insertion target [F1-F4].

Tap-for-Paste: **expected** at its caret, possibly a second tap. | Double-tap/handles/Copy: **expected**, but first gesture may focus the layer and raise the keyboard. Tap-for-Paste: expected at caret; first tap normally focuses/raises keyboard. | Two editable roots compete unless this layer becomes the sole iOS input owner. Tap-for-Paste: expected after focus/caret placement. | `textarea.value` is separate from xterm’s rendering and input buffer. Do not blur the textarea to show Copy: the phone log says it erased selection. Native first focus is expected to raise keyboard. Physical iPhone must confirm all four gestures in both states. [S9, S13-S20] |

First prompt tap may raise keyboard; repeated tap may be needed for Paste. | PR keeps DOM rows selectable, bypasses competing xterm mouse selection when mouse reporting is off, and enlarges the helper target [S23]. This could delete the mirror but is not a small local change while PR remains open with requested changes. It still splits read-only output from editable input; keyboard-shown Copy is unknown. **Practice evidence.** xterm issue #3727 records an iPad report that neither DOM nor canvas/WebGL modes selected text by touch; that is a first-hand report, not a cross-version test [S24]. PR #5961 remains open and its author reports native long-press selection/Copy and Paste on iPhone Safari; its reviewer requested changes [S23]. A downstream Home Assistant/ttyd integration reports success using an explicit DOM-selection mode, but this is another contributor report and does not establish double-tap or keyboard-shown Copy [S23]. Pyco/pycoterm reports a separate overlay activated by long press, close to localssh’s existing layer [S24]. No primary documentation found for VS Code web/Codespaces, Wetty, Blink Shell, Termius web, or hterm proves the exact four gestures in **both** keyboard states. Their existence is not evidence that this requirement is solved [S24].

### Q4. Smallest defensible architecture, **MED** for decision; **LOW** that it will fully pass without device work

- **F12 PROBABLE.** The smallest architecture plausibly meeting **all four gestures in both keyboard states** is option 1: adapt the existing mirrored DOM layer into the **sole iOS editable selection and input surface**, while xterm remains the renderer and terminal protocol engine. This avoids two competing editable roots and reuses the row synchronization already present [F5, F8-F9, S18-S19]. It needs a bounded input/IME and paste-once integration; it is not a CSS-only fix or a passed device result. Option 3 is the smallest diagnostic diff but the keyboard-shown Copy observation and WebKit’s historical non-editable double-tap rule make it an insufficient release recommendation [F5, F8, S9, S19]. Option 2 duplicates more xterm state; PR #5961 is a design reference but does not prove the keyboard-shown case [S23-S24].
- **F13 PROBABLE.** A genuinely single-tap Paste menu cannot be promised for an initially unfocused field. The acceptance test should say: with keyboard shown and caret already in the editable target, tap the caret and choose Paste; with keyboard hidden, tap once to focus/place caret, then tap the caret and choose Paste if the menu did not appear on the first tap [F3, S1-S2, S7]. This preserves the user’s intended *location* while respecting documented focus behavior.

## Five-minute physical-iPhone test

1. Record iPhone model, iOS version, Safari version, and page URL. Copy `alpha beta gamma` from another app. Open the live terminal with a visible output line containing three words and a fresh prompt. Note any first-login rectangle.
2. **Keyboard hidden:** Double-tap `beta` in output. Record whether one word highlights, handles appear, handles extend through `gamma`, and Copy appears. If no menu, tap the selection once and record whether it appears. Copy and paste into Notes to verify exact text.
3. **Keyboard hidden Paste:** Tap the prompt insertion location once. Record whether keyboard opens and whether Paste appears. If absent, tap the same caret once, then try touch-and-hold. Choose Paste. Verify exactly one insertion and, in a bracketed-paste-aware shell/editor, that it follows the bracketed path.
4. Leave keyboard **shown**. Double-tap output `beta` again. Record selection, handles, adjustment, Copy, and whether keyboard remains shown, closes, or flickers. Copy to Notes to verify text. Do not dismiss or blur the terminal field during this step.
5. With keyboard **shown**, tap the prompt caret once, then a second time only if needed. Record whether Paste appears, whether it inserts once, and any keyboard movement. Repeat a long press on output only as a diagnostic. Capture the on-screen event log for `focusin`, `focusout`, `selectionchange`, `pointerdown`, and `paste`; a DOM range alone does not count as a pass.

Pass requires double-tap word selection, adjustable native handles, working Copy, and Paste from the caret in **both** initial keyboard states. Note any keyboard opening, closing, or flicker; first focus opening the keyboard is an expected platform side effect, but losing selection or a menu is a failure. Test on plain HTTP, because the secure-context clipboard API cannot rescue a failed native Paste [F11].

## Gaps and assumptions

- **G1.** No device or WebKit test matrix for iOS 17-26 was available. Historic WebKit decisions may have changed; current Safari UI behavior must be observed on the target versions.
- **G2.** Apple does not specify one universal tap count for showing Paste in an unfocused Safari textarea. Test focus, caret, and clipboard availability separately.
- **G3.** The exact cause of the reported first-login rectangle is unknown. A screenshot and computed styles can identify it.
- **G4.** No independent evidence confirms double-tap selection or Copy with the keyboard shown in localssh, xterm PR #5961, or the cited downstream reports.
- **G5.** No source proves that a programmatically created DOM range gets native handles and callout on every iOS version. The local long-press fallback is not a substitute for device verification.

## Limitations

This report uses published sources and local code, not a physical iPhone run. WebKit `main`, open PR status, Apple guides, and Safari behavior can change after **2026-11-02**. The older WebKit changesets establish historical behavior but not an iOS 17-26 version matrix. No single-source device report is treated as an established result.

**Recommendation.** Prototype the existing mirrored text layer as the sole iOS editable interaction surface, with xterm still rendering and handling terminal protocol input [F12]. First use the five-minute device test to confirm the current split’s failure modes and identify the opaque textarea rectangle. The prototype must route typing, composition, and native Paste exactly once, keep output selectable during terminal updates, expose an accessible input surface, and preserve desktop behavior. A hidden-keyboard double-tap may raise the keyboard; a tap-for-Paste in an unfocused field may need a second caret tap [F1-F3, F13]. Release only after the physical iPhone passes selection, handles, Copy, Paste, and keyboard stability in both initial states; the available sources cannot certify that outcome [G1-G5].
